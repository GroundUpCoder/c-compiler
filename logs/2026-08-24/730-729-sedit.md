# #730 + #729 (+ discovered #734): sedit Ctrl+G data loss, vacuous acceptance instruments, and the dialog that cancelled itself

Lane: `lane/730-729-sedit` off `origin/main` @ `e0f05fdf`. Fable implementation
thread; independent Codex review to follow per the standing rule.

## #734 — the discovery that reordered the work

Writing #730's regression test required driving the Go-to dialog with
`wmctl settext EDIT:1`. Reading the path first (per the hypothesis rule):

- `os/win32/user32.c` `edit_notify` sends the parent
  `WM_COMMAND MAKEWPARAM(id, code)` for EVERY notification, and the EDIT's
  `WM_SETTEXT` handler fires `EN_CHANGE` (0x0300) — as does every insert.
- The Go-to/Find dialog input EDIT is control id **2 == IDCANCEL**
  (`windows.h` IDOK=1, IDCANCEL=2).
- `GotoProc`/`FindProc` matched `LOWORD(w)` only.

So any text change — one typed character, or the e2e's settext — arrived as
`LOWORD==IDCANCEL` and cancel-closed the dialog. **Interactive Ctrl+G and
Ctrl+F never worked**: the first keystroke dismissed the dialog and the rest
of the typed text fell through into the document. The e2e's two goto-dialog
legs passed vacuously (dialog self-cancelled, `click Go` no-opped, and the
asserts only checked "document unchanged" — trivially true). A fourth vacuity
beyond #729's three, hidden by the same class of weak assert. Filed as **#734**
(P0, contract violation in the shipped #718 headline flow), fixed here first
because both tickets' acceptance tests are unwritable without it.

Fix: both dialog procs act only on `HIWORD(w)==BN_CLICKED` (the modal
keyboard path already sends bare IDOK/IDCANCEL, HIWORD 0). The two existing
e2e legs gained waits on the error boxes they were always meant to observe,
so a re-broken dialog now times the wait out and driveBoot fails loudly.

Observation, not fixed (usability gap, no contract text): `prompt_line`'s
modal loop — unlike `prompt_find`'s — does not map VK_RETURN/VK_ESCAPE to
Go/Cancel, so keyboard-only Go-to needs a mouse click on Go.

## #730 — cross-file Ctrl+G gates on may_close()

Exactly the ticket's shape: every other document-replacing path prompts;
the Go-to cross-file branch called `open_path()` directly. The guard now
sits after the realpath existence check (a bad location stays loud without
a save nag), only on the cross-file branch:

```c
if(strcmp(real,doc.target_path)){if(!may_close())return 0;return open_path(path,line);}
```

Cancel ⇒ `return 0`, buffer/caret/target untouched. No ⇒ navigate, edits
deliberately dropped, nothing written to disk. Yes ⇒ `save_doc(0)` then
navigate. Same-file Go-to never reaches the branch. One accepted asymmetry:
Yes saves *before* `open_path`'s beyond-EOF validation, so a Yes answered
into an invalid target still saves — a save is never harm, and ID_OPEN has
the same prompt-then-maybe-fail shape.

e2e legs (test_sedit_e2e): fresh single sedit (unambiguous `EDIT:n`),
`settext` establishes a known-clean baseline (WM_SETTEXT clears the modify
flag), one typed key dirties it deterministically at caret 0, then
Cancel / No / Yes runs each pin buffer + status target + on-disk bytes.
The dirty same-file run is pinned prompt-free by wait-text on the status
line (Line 1 → Line 2 proves the navigation completed, which proves
prompt_line returned un-blocked) plus a `nolabel "Save changes?"` absence
check — no expected-timeout waits anywhere.

## #729 — the three vacuous instruments, replaced with executing coverage

Principle applied throughout: if the mechanism cannot execute in a cheap
harness, extract it into the executable core the repo already keeps for
exactly this purpose (gucedit_core.c; the #728 styles.c extraction is the
precedent), call the extraction from production, and execute it in the probe.

1. **test_gucedit.js, six `regex.test(user32.c)` legs — deleted.** The
   generation step was extracted (`gucedit_generation_advance`,
   gucedit_core.c; `edit_notify` calls it) and gucedit_probe.c now executes
   it: advance on byte change, no advance on identical bytes, baseline
   tracking, length change, empty transitions, wrap skipping generation 0.
   Leg-by-leg accounting of the six:
   - "generation is exact-byte-change bound at EN_CHANGE" → probe-executed.
   - "stale generation has distinct error" → core distinctness
     (CHECK_STALE vs CHECK_INVALID) was already probe-executed; the
     handler's mapping to `GUCEDIT_ERROR_STALE_GENERATION` is wiring
     (below).
   - "delegates validation to core" / "uses replacement core" → wiring;
     the wired pipeline (EN_CHANGE advance → GEM_SETSTYLES validation →
     styled paint) is pinned end to end by the new big-file e2e leg and
     the repaired os-sedit.mjs leg — both execute the production binary.
   - "destroy frees styles" → **review-only now.** Malloc hygiene in a
     non-instrumentable production path: no cheap harness can observe the
     free, and the regex only ever matched characters (the audit proved a
     dead comment kept it green). The core's free-prior behaviour
     (`gucedit_replace_batch`) stays probe-executed under ASan reachability.
   - "test allocator override is compile-time only" → its behavioural half
     (baked wasm exports no test symbol) was already leg 15 and stays.
2. **test_sedit_core.js:9 scan-bounds regex — deleted.** The bounded turn
   was extracted (`sedit_scan_turn`, styles.c; `restyle_step` calls it with
   a CLOCK_MONOTONIC adapter) and sedit_core_probe.c executes it under an
   injected clock: 262144-byte turn cap, 32768-byte chunk granularity
   (clock-call count), 8 ms time cap, chunked-turns == one-feed oracle
   (token AND pair map equality). The posted-turn wiring — restyle_step
   re-posting WM_RESTYLE — is pinned by the new e2e leg: an ~414 KB
   generated C file is past one turn's byte cap, so styled pixels
   (TYPE purple 95,0,111 / COMMENT green 0,100,0, read back via
   readShots/#657) can only appear through several posted turns plus
   publish + GEM_SETSTYLES + styled paint. The 8 s pre-shot settle is a
   genuine no-marker settle (publish has no external marker) and is
   annotated as such in the script.
3. **os-sedit.mjs:22 tty-echo witness — replaced.** After Find selects the
   match, the test types `XFINDX` into the selection; the gettext witness
   `/* green */ XFINDX 0;` exists only if Ctrl+F really selected exactly
   `return` and focus really returned to the document EDIT. Nothing ever
   types that document text on the tty, so the echo cannot satisfy it.
   (Under the pre-#734 product this leg would sit RED — the find dialog
   closed at the first typed character; that is the leg doing its job.)

### The ticket's standing-guard question

Should a cheap standing guard catch the `regex.test(<source>)` shape
generally? **Answer: over-reach — don't build it.** The repo legitimately
asserts over source text in places (drift checkers, PORTS.md generation,
registry set-equality guards); the defect class is "a test asserts the
wrong OBSERVABLE", and no static scan can classify observables. What
actually catches the class is the discipline this lane followed: mutation
as the acceptance standard for every new or repaired test, recorded in the
dev log. A lint that flags `readFileSync` of production sources inside
`tests/` would drown in legitimate hits (probe compiles read sources by
path, drive.js reads image.json, ...).
