## FINDINGS

1. **BLOCK — compositor shows a never-uploaded texture on SH_LOCK contention right after a reconfigure.** `os/compositor.js:363-376` (tip). `shmBindFor` first replaces the cache when `(w,h,gen)` changed: line 363 `c.tex.destroy()` destroys the previous good texture, line 368 creates a fresh entry with `seq: seq - 1` and a brand-new (zero-initialised) GPUTexture. Only THEN does it try-lock; on contention (line 373) it sets `uploadRetry` and returns `c.bind` (line 376) — the bind of the fresh, empty texture. Scenario: SURFACE_CONFIGURE commits a new SAB and `_bumpWm`s; the compositor's next `draw` sees the new gen; the producer (in a storm, presenting at full rate) is inside `wmShmFlip` holding SH_LOCK at that instant; the compositor draws one frame of the surface as transparent black at the new geometry. That contradicts the file's own comment ("the previous valid frame stays on screen"), WM.md's "contention = keep the last good frame", and the contract's "Keep the previous valid frame until replacement is accepted". Coverage: this branch is exercised by NOTHING — `shmContended` is 0 in all six of the author's evidence.json runs and the browser test only records it; there is no unit-level test of `shmBindFor` at all. What would satisfy me: keep the previous cache entry (and its texture) alive until the first SUCCESSFUL upload of the new generation — e.g. create the new texture but only swap it into `shmCache` after the locked copy + `writeTexture`, or on contention with a fresh entry return the OLD bind and destroy the old texture only after the upload lands; plus a test that drives `shmBindFor` with a fake `device`/`surf` (startCompositor's `device` is injected, so a Node fake with `createTexture`/`queue.writeTexture` recording calls is feasible; a red control = the current code returning a bind whose texture never received a `writeTexture`). If a Node harness for compositor.js is genuinely impossible, say so and pin it with a browser leg that forces contention (a wedged SH_LOCK on a surface for one rAF via a probe) and asserts the pixels are still the previous frame's colour.

3. **minor — the stale-ack error shape is not one shape.** `kernel.js:5077` returns EINVAL for ANY ack when `!sc.pendingConfigure`, so the identical retired-serial ack is ESTALE while some other configure is pending (5104-5107) but EINVAL once the queue is empty (test_wm_frames B "a second ack with nothing pending -> EINVAL" pins this). The contract says rejected commits return stale-configuration; the host treats both the same (keeps the old buffer) except that `staleAcks`/`configureStaleCount` miss the EINVAL flavour. Also the decline path's ESTALE (5083) is not counted by `_wmCfgStaleN`, while WM.md says ESTALE is "counted host- and kernel-side". Satisfy: ESTALE whenever the serial is not a still-valid issued one (regardless of pending), EINVAL only for malformed requests/SABs; count every ESTALE; update the two test legs (two-sided edit).

4. **minor — `_wmFrame` size rejection is a behaviour change for gpu producers, not just a serial check.** `kernel.js:5913` now closes a bitmap whose size != the committed surface size. Before #790 `gpuBindFor` (compositor.js:397-417) imported a bitmap at ITS size and drew it into the surface rect, i.e. scaled it; only `captureSurface` required equality. Any gpu producer that ships a canvas of another size (raw webgpu.h apps size their own canvas via `__wgpu_surface_configure`) now goes blank instead of scaled. Evidence: `framesRejected` is 0 in all ui-frames runs (SDL gucos renderer only). Satisfy: state the intended contract in WM.md (a gpu frame must be the committed size — reasonable and honest) AND show `framesRejected` stays 0 for the raw-webgpu case (gpubox) — an assertion in os-gpubox.mjs or a recorded run.

5. **minor — the under-load evidence claim is not in the record.** The kickoff says "author ran it 3/3 under load x10". 6. **minor — host-side `flipMisses` is a probe nobody reads outside the unit test.** `host.js:7598` `wmShmFlip` proceeds UNLOCKED after ~64 x 1 ms waits (bounded, documented, counted) — that is the one place the "producer cannot overwrite storage the compositor reads" guarantee is deliberately relaxed. `frameStats()` is exported on the surface object but no e2e/browser test asserts `flipMisses === 0`; the browser test asserts only the kernel-side `shmLockMisses`. Satisfy: expose the per-process count to a probe the browser test can read (kernel-worker stats or a wmctl/GET_STATE field) and assert 0 per driver, so a regression that makes the consumer's section long shows up.

## Verified clean (what I checked and found correct)

- (a) Serial state machine: accept requires `serial in issued && serial > committed && dims == issued dims && SAB W/H/GEN match`; commit filters `issued` to `> serial`, so no interleaving of superseded acks, declines, retirement at the bound, or destroy/exit moves geometry backward or leaves `issued` non-empty with no pending target (the storm in test_wm_frames J checks exactly these invariants after every op, 300 ops, seeded; passes). `_wmIssueConfigure` rolls back `issued`/`pending` on EAGAIN and never reuses `cfgSerial`. Equal-size regeneration is a real configure (wmResize only no-ops when nothing is pending) and a new gen; the host allocates a fresh SAB and acks on its first same-size present. SAB dims == surface dims is swapped in one kernel turn.
- (b) SH_LOCK: producer reads FLIP, writes the back buffer unlocked (only it flips, so back is stable), flips under the lock; consumer holds the lock across its copy, reading FLIP and re-reading SEQ under it (compositor.js:381). No nested acquisition on the kernel thread (compositor releases before writeTexture; wmScreenshot is the ONE kernel-side front-buffer read — verified by grep: one SH_FLIP load in kernel.js). Kernel spin bound 200000 CAS ≈ 1.2-1.8 ms measured; producer wait bound 64 x 1 ms; both fall back unlocked and COUNT it. Atomics.wait is caught for a main thread; host.js's surface backend never runs on a browser main thread with a kernel consumer. All three shm present sites (shmPresent, sw renderer present, Dawn tail) flip through `wmShmFlip`. test_shm_ownership: 335 concurrent frames, 400 locked reads, 0 torn, 0 misses; red control tore 1 in 12 reads with the pre-#790 flip — the instrument is real.
- (c) wm-sabs: SURFACE_CONFIGURE clears `pcb._wmPendingFb` at entry on every path (decline, EINVAL, ESTALE); process exit clears it; a decline posts no SAB. test_wm_frames L pins the decline case.
- (d) Legacy: pre-#790 wasm never sees serials (host.js consumes ring word [4]; `__sdl_push_window_event` still gets w,h). A frame without a serial keeps the size check only. wm.c reads EV_CONFIGURED into `int32_t p[8]` (os/wm.c:4040) so the 4th word fits; unknown 0x97 falls to `wmp_skip` (4245). The only other EV_CONFIGURED emitter is the #789 probe fixture (3 words, still valid). Image bumped 294->295 (wm_proto.h and the SDL veneer are bake inputs).
- (e) SDL3 shape: `SDL_GetWindowSizeInPixels(bool, out w/h)`, `SDL_GetWindowPixelDensity`/`SDL_GetWindowDisplayScale` (float, 0.0f on failure) match SDL3's signatures and semantics; 1:1 is the true platform answer (1 buffer px = 1 screen px, WM scaling is presentation policy the app never sees). Nothing SDL-named is approximated; the geometry epoch rides the kernel ring only, as the plan said. sdl-api-index regenerated and its --check test passes.
- (f) Tests: 69/6/25 new checks, none vacuous that I could find (the storm asserts >20 acks/>5 stale/>3 declines so it cannot pass idle; the wedged-lock legs assert the miss count moved; the red control is stop-on-first-tear). The browser test settles on exact pixel counts with a capture loop, not naps; every phase in the evidence settled in 1-2 captures with stale 0. Two-sided edits present in test_wm/test_wm_policy/test_wm_anchored.
- (g) Acceptance coverage: storms/equal-size (J, E, browser storms 1-3), stale ack/retirement (C, D), slow compositor vs fast producer (test_shm_ownership with real threads — kernel consumer; the BROWSER consumer's contention branch is the gap in finding 1), allocation failure (F + host decline leg), in-flight destruction (G), CPU+GPU graphical evidence with sha256 identities and the installed VERSION_ID pinned to the manifest (evidence.json).
- (h) Docs: KERNEL.md/WM.md/wm_proto.h/kernel.js header comments match the code except finding 2 and the counting claim in finding 3. `node tests/run.js --diff 7799eb32 --dry-run`: no UNMAPPED paths; compiler.js pulls all suites as expected.
