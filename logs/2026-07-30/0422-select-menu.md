# 0422 — the core select menu is ON in gucOS

A `<select>` click reached neither of NetSurf's two menus. The core menu
sat behind `nsoption_bool(core_select_menu)`, false by default and never
set. The frontend menu needs a `create_form_select_menu` window-table
entry that gucOS does not supply. The fix takes the core menu, per the
ticket's plan: one `nsoption_set_bool(core_select_menu, true)` in
`gucos/main.c set_defaults` (the `enable_javascript` precedent, so
Choices and the command line still read over it). The option also WIDENS
the closed widget: `layout.c` adds `SCROLLBAR_WIDTH` (16 px) to the box
when it is on. Image v195 → v196.

## The one real bug: the mutation bridge ate its own menu

The first run of the new e2e passed every single-select leg and failed
every multi-select leg: the first toggle CLOSED the menu. The cause is
an interaction between two correct pieces of project code:

- `form__select_process_selection` writes the toggle back into the DOM
  with `dom_html_option_element_set_selected`. That sets or removes the
  `selected` ATTRIBUTE, and libdom dispatches the mutation events
  synchronously, inside the call.
- The gucOS mutation bridge (`dom_event.c`,
  `DOMSubtreeModified` → `html_schedule_reconvert`) treats an attribute
  change as a render-tree edit. A re-conversion destroys the menu by
  construction (`box_select` refills the option list;
  `form_select_clear_options` frees the menu object).

So every multi-select toggle re-boxed the document and dismissed the
menu under the click that made it. Single-select never showed the
problem because its menu closes on the pick anyway.

The bridge already carries the exact precedent: TEXTAREA/INPUT value
edits set `reconvert = false` because "a whole-document re-box per
keystroke would destroy the textarea widget (and caret) mid-edit". The
select case is the same class, one step removed: the mutation TARGET is
the option, but the widget it would destroy is the select's menu. The
fix is a self-mutation guard, not a tag carve-out:
`html_content.form_selfmutation` is non-zero exactly while
`form__select_process_selection` runs its `set_selected` loop, and the
`DOMSubtreeModified` callback skips the reconvert while it is set. The
form code has already rendered everything those writes change (box text
via `form__select_set_box_text`, box redraw, menu repaint), so nothing
is lost.

The guard is deliberately NOT a blanket OPTION/SELECT carve-out: a
JS-originated `option.selected = true` still takes the reconvert path,
because there the render state really is stale and the re-box is the
mechanism that refreshes it. An open menu dies under such a JS write —
that is the ticket's recorded deferral (menu-survives-reconvert needs
the 0407 focus treatment plus a diffed option list), unchanged here.
The ticket's notes end by saying the deferral becomes decidable "once
the menu exists at all"; it now exists, so that decision is due with
the coordinator, not silently dropped.

## Test shape (`test_netsurf_select_e2e.js`)

Geometry is MEASURED, never derived from font maths: a first session
opens the menu and shoots it; Node reads the selected-row highlight
band (`SELECT_SELECTED_COLOUR` 0xDB9370, byte-order variant detected,
fill rects are exact and `[y0,y1)`-exclusive) out of the PPM to get the
menu origin, row pitch and scrollbar edge; a second session over the
same image replays deterministically with computed coordinates —
client coordinates, so window placement cannot matter.

- The layout half is a DIFFERENTIAL: the same page in a
  `--core_select_menu=0` window, widget width measured off a
  shrink-wrapped float wrapper's padding strip; ON − OFF must equal
  exactly 16. The OFF window doubles as the pre-fix control: its click
  must paint NOTHING.
- Scroll is exact, not "something moved": a scrollbar arrow PRESS
  scrolls exactly `SCROLLBAR_WIDTH` (`scrollbar.c`), so six clicks are
  96 px; the row-2 band must sit exactly 96 px higher, and a click at a
  computed y must pick index 5 through the scrolled row mapping
  (`form_select_menu_clicked` arithmetic), reported back through a
  change listener that paints an index-encoding colour.
- Open/close is an occlusion oracle: a probe-coloured block under the
  widget reads ~0 inside the menu rectangle while open, and returns to
  baseline on close.
- The multi page has NO change listener: a DOM write from JS while the
  menu is open would re-convert and dismiss it (the deferral above).
  Toggles are asserted from the highlight bands; the final DOM state is
  painted by a button clicked after dismissal.
