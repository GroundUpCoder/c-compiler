## #501 — wmctl strict numeric-operand validation (`c1840cf5`)

The kickoff said the geometry verbs "correctly reject a non-numeric argument"
and to "find and reuse" that validation. **Corrected: there was no client-side
validation anywhere in wmctl.** Every verb used bare `atoi()`; `focus pong`
only failed loud because the KERNEL rejects sid 0 for geometry ops, while the
injection verbs define sid 0 as "the focused window" — so the same `atoi`
slip is loud on one family and silent on the other. Measured on the old
binary via boot.js: `wmctl key pong 44` is even *timing-dependent* (rc 1
before anything has focus, rc 0 after), and `wmctl wait gone pong` was an
INSTANT false green (sid 0 is never listed) — the worst of the lot, in the
one verb the whole estate uses as its sync primitive.

Design calls:
- **Strict validation (kickoff option a), not name resolution (b).** Nothing
  in the tree resolves a window NAME to a SID today (`wait win TITLE` matches
  titles but never returns a sid to a caller); (b) is new surface wanting its
  own ticket.
- **All numeric operands validate, not just the SID** — the Pass B comment on
  the ticket showed a valid-SID/non-numeric-SCANCODE repro (`wmctl key 3
  space`), so `need_i32`/`need_f` (fractional wheel) cover scancode/keysym/
  mod/coords/counts/wait-MS/WxH too.
- **Exit 2** (the header's documented usage-error code), message naming the
  argument: `wmctl: key: 'pong' is not a numeric SID (see wmctl list)`.
- Unknown verbs still get `usage()` (a sid-verb membership check runs before
  the SID parse), and sid 0 stays valid.
- `wait dim/dst` also got an up-front WxH shape check — a malformed WxH used
  to spin the full timeout ("keep waiting" forever per poll).

Estate audit before the change: every wmctl call site in tests/os/vendor/
tools passes numerics, shell-expanded numeric vars, or label forms (agent
path, no SID parse). Nothing newly fails.

Controls: measured old-binary rcs (0/1) vs new (2 + stderr); the five new
`|| echo 501-*-$?` legs in test_wm_service_e2e.js stay silent on a pre-#501
binary, so the JS checks go red there. Image v238 → v239 (wmctl.c is a
seeded source).

## #146 — nanosleep(0) 1 ms JSPI floor removed (`130bddfd`)

Three flavors, not two: JSPI (`Math.max(1, ms)` — the outlier), block-FS
(`blockingSleepMs`, documented no-op at ≤0), and the kernel-client park
flavor the ticket didn't name — `KernelClient.park(0)` computes a
non-positive deadline and returns 'timeout' immediately, so it was already
POSIX-correct. The floor is not load-bearing: `usleep(0)` on the same JSPI
path already does `setTimeout(0)`, and a 0 ms timer yields the macrotask
queue exactly like a 1 ms one. Removed it; both `nanosleep(0,0)` (×20) and
the 0.5 ms pass-through are now asserted on both backends in
test_sleep_clamp.js, whose KNOWN GAP block is gone. Red control: the new
assertions fail on the pre-fix host.js (all twenty zero-requests read 1).
**Ticket correction: the register entry is L55, not L53.** L55 retired
(42 → 41 entries).

## #489 — 5 s hung-app grace: validated where testable, accepted where not (`c9b80484`)

The watchdog's only observable is input-ring rpos advance, so a
starved-but-healthy app and a wedged one are indistinguishable BY DESIGN —
"reproduce real starvation" and "reproduce a wedge" have the same observable,
and the wedge is already the #486 wedged leg. What was genuinely untested was
the boundary's green side: a SLOW consumer whose first drain comes mid-grace
(after several poll ticks, unlike the instantly-draining polite leg) must
survive — that is the false-positive regression a poll bug would produce.
New test_wm.js leg pins it; red control measured (drain removed → the leg
fails with the process zombie'd and the titled reason logged).

The acceptance is written at `WM_HUNG_GRACE_MS` in kernel.js: what #486
measured under load (7 close-issuing e2es spanning every app family — NB
~29 files issue closes, so the coverage is by family, not by file), why >5 s
ambient starvation is unproducible (the OS timeslices pegged cores), the
by-design indistinguishability, the existing observability of real fires
(the `_wmForceQuit` `_log` reason — no new counter API; a counter with no
reader is surface, the log line already makes fires visible in boot stderr
and the browser boot console), and the ticket's do-not-tune rule restated
where a future fixer will actually be looking.
