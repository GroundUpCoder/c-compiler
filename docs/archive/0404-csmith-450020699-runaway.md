# 0404 — csmith seed 450020699: wasm run 1500x slower than native (hang-class)

- **Status**: done (2026-07-29 — not a miscompile; the live tier's oracle was
  unsound. Fix: width-normalize literal suffixes in tests/run.py, guard ILP32
  literal typing in tests/unit/conformance/ilp32_long_literal_typing, seed the
  program into the corpus as c450020699.c.)
- **Design**: —

## Resolution — the mechanism

The compiler is correct. The two toolchains ran two different programs.

The native oracle is host clang, an LP64 compiler: `long` is 64 bits. Our
compiler targets wasm32, an ILP32 platform: `long` is 32 bits. C11 6.4.4.1p5
types a hex constant with the suffix `L` as the first fit of `long`,
`unsigned long`, `long long`, `unsigned long long`. The seed contains the call
`func_18((~g_4) >= 0xD7D41305L)` with `g_4 == 0`. On LP64 the literal is a
signed 64-bit `long`, so `-1 >= 3620999941` is false and `p_19` is 0. On ILP32
the literal does not fit `long` and becomes a 32-bit `unsigned long`, so the
compare is unsigned: `0xFFFFFFFF >= 0xD7D41305` is true and `p_19` is 1.
`clang -target i686-pc-linux-gnu` folds the same expression the same way as
our compiler.

With `p_19 == 1`, `func_18` enters block 102. That block holds
`lbl_235: ... if (g_122) goto lbl_235;`, the loop body does not write `g_122`,
and `g_122` is -3 there. The correct ILP32 execution therefore never
terminates. Csmith only bounds its `for` loops; a value-dependent `goto` loop
terminates only under the width model that the recorded execution used.

Proof of closure: rewrite all 273 `L`/`UL` literal suffixes in the seed's
program to `LL`/`ULL` (a semantic no-op for LP64 clang), and our wasm build
completes in ~0.1 s with the exact native checksum `65817AB`. The suffix
rewrite is also complete for this generator configuration: the only bare
`long` in csmith output is the unused `__undefined` sink, and the corpus
contains no `sizeof`.

## Resolution — the fix

1. `tests/run.py` gains `normalize_long_literals`: both fuzz tiers compile a
   width-normalized copy (`L`/`UL` → `LL`/`ULL`) on BOTH sides. The rewrite
   is a no-op for the LP64 oracle, so the recorded tier-1 checksums stay
   valid, and the wasm side sees the oracle's literal types.
2. `tests/unit/conformance/ilp32_long_literal_typing` pins the ILP32 literal
   typing rules themselves (born green — verified against clang i686 constant
   folding, since an LP64 oracle cannot check them by construction).
3. The seed's program is committed as corpus entry `c450020699.c` with the
   native checksum in `manifest.json`, so the acceptance runs on every fuzz
   pass: 106/106 green (101 corpus + 5 live).

## Goal

The fuzz suite's live tier flagged `fuzz/live-450020699` with `run timeout`
during the 0398 gate (2026-07-29), and the seed REPRODUCES deterministically:

- native (clang -w): checksum `65817AB` in **0.48 s**
- our toolchain: compiles clean, but the wasm run was killed at **>12 min**
  (the suite's cap is 60 s) — >1500x native, far beyond any wasm-vs-native
  factor, so a hang-class (or pathologically slow) miscompile is suspected.

Not introduced by 0398: that branch touches no compiler path (`compiler.js`
unchanged vs `ab6dcc78`; the `host.js` delta is the inert `__egress` import
stub). The live tier draws random seeds per run, so this seed simply had
never been drawn before.

Reproduce:

```
csmith --seed 450020699 --max-funcs 4 --max-block-depth 3 \
  --max-array-dim 2 --max-array-len-per-dim 4 --max-struct-fields 6 \
  --max-expr-complexity 8 --no-packed-struct -o fz.c
clang -w -Ivendor/csmith-corpus/runtime fz.c -o fz_n && ./fz_n   # 0.48s
node compiler.js fz.c -Ivendor/csmith-corpus/runtime -o fz.wasm
node --experimental-wasm-exnref host.js fz.wasm                  # >12min
```
